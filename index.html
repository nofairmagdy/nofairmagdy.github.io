Project details

Master's thesis, TH Ingolstadt, graded 1.0

Licence plate detection and rectification with polygon localisation

The problem

Cameras rarely see a licence plate head-on. A bounding box around a tilted plate includes background and keeps the distortion, which makes the characters harder to read. Small and distant plates add a second problem: they can disappear on a coarse prediction grid.

Approach

The model follows WPOD-Net. For each cell of the output grid it predicts whether a plate is centred there and six affine parameters that map a unit square onto the plate's four corners. The corners then drive a perspective transform that unwarps the plate.

I studied how the stride of the output feature map affects detection, comparing the original stride 16 with stride 8, and then added a lightweight feature pyramid that fuses upsampled stride-16 context into the stride-8 map. The model was trained on the public CCPD dataset (about 250,000 images) and transferred to a custom THI dataset (about 13,000 images) with day, night and snow conditions.

What I implemented

  • Three model variants in PyTorch: base WPOD-Net at stride 16, at stride 8, and the feature-pyramid variant at stride 8.
  • The training loss: cross-entropy for plate versus background plus a smooth L1 loss on the corner coordinates.
  • A top-K decoding step that turns the best-scoring cells into corner polygons.
  • The data pipeline with Albumentations: resize and pad, then rotation, perspective, brightness and contrast, CLAHE, motion blur and noise augmentation.
  • Training with learning-rate warm-up and cosine decay, mixed precision, EMA weights, resumable checkpoints, and staged freezing and unfreezing of layers for transfer learning.
  • Evaluation with polygon IoU, precision, recall and mAP, including cross-dataset tests from CCPD to the THI data.
  • Inference and inspection scripts for debugging what the model predicts at each stage.

Result

Reducing the stride from 16 to 8 improved localisation, most clearly for small and distant plates. The feature-pyramid variant at stride 8 performed best and became the final model. The thesis was graded 1.0.

Proof of concept, September 2026

AI agent for triaging HIL test logs

The problem

A nightly HIL run on E/E components leaves a pile of failed test cases. Some point to real software defects. Others come from the bench itself and only need a re-run. Sorting them by hand each morning is slow, and bench problems filed as bugs waste developer time.

Approach

The project has two parts that share one core. A text classifier assigns each error message to a failure type: CAN timeout, signal mismatch, active DTC, flash error, or environment (a bench or tooling problem). A LangChain agent then uses that classifier and the log files through tools exposed by an MCP server, checks whether failures cluster on one ECU or bench, and writes a markdown triage report.

[INFO ] Bench: HIL-07 | ECU under test: EPS | SW: 25-08-984
[INFO ] Step 2: stimulate SteeringAngle
[ERROR] Fault memory check failed: EPS reports DTC 0xCCE21E confirmed
[INFO ] Verdict: FAILED

The logs and training messages are synthetic: 38 generated HIL logs and 1,250 labelled error messages. No real test data is involved.

What I implemented

  • A scikit-learn pipeline with word and character TF-IDF features and logistic regression. Predictions below a confidence threshold go to a "needs review" group instead of a class.
  • An evaluation that holds out whole message templates. A random split would leak the same phrasing into training and test and report misleadingly high accuracy.
  • A FastAPI service with validated request models for single and batch classification, per-log analysis and whole-run triage.
  • An MCP server with seven tools, and a LangChain agent that discovers them at runtime and works with OpenAI, Anthropic or a local Ollama model.
  • Path checks on every tool that takes a file name, because the caller is a language model.
  • API tests with pytest and an offline end-to-end test that runs the whole agent loop with a scripted fake model, so no API key is needed.
  • A transport fix: the stdio connection froze on Windows, so the server now uses streamable HTTP.

Motion planning and control, 2025

Evasive manoeuvre planner

The problem

When braking alone will not avoid an obstacle, a driver assistance function can steer around it. The path has to move the car sideways within the available time, stay smooth enough to be drivable, and bring the car back to its lane.

Approach

The planner splits the manoeuvre into five segments: drive straight, swerve, hold the offset, return, and drive straight again. The swerve and the return are quintic polynomials, which start and end with zero lateral velocity and acceleration. The time allowed for the swerve is derived from the time to collision.

A second script checks that the path can be followed. A kinematic bicycle model represents the vehicle, and a PID controller steers it using the lateral error to the nearest point on the reference path.

What the code contains

  • A quintic polynomial solver for position, velocity, acceleration and jerk.
  • Generation of the five-segment lateral path from the time to collision, written out as a reference trajectory.
  • A discrete kinematic bicycle model with steering angle and acceleration as inputs.
  • Positional and incremental PID controllers with output limits.
  • Path tracking with a KD-tree for the nearest reference point, and plots of the planned and driven paths.
